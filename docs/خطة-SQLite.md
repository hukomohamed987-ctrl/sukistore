# خطة نقل الحفظ من JSON إلى SQLite

## الوضع الحالي (اتأكدنا منه في الملفات)
- Node 24.20 + Express 5.3. كل الحفظ بيعدّي من `database/db.js` (كلاس `Collection`، 31 مجموعة، 13 دالة: getAll / find / findOne / getById / findById / insert / update / delete / count ...).
- حوالي 700 استدعاء في 23 ملف route، كلهم بنفس الدوال دي. مفيش route بيكتب في ملفات JSON مباشرة.
- استثناءات بتكتب في الملفات مباشرة (يدوية، مش وقت التشغيل): `scripts/reset-trial-data.js` و `database/seedNewCatalog.js` (مش مستخدم).
- عيب في الحالي: `update` بيقرا الملف ثم يكتب بعد انتظار → طلبين في نفس اللحظة ممكن واحد يمسح تعديل التاني (lost update).

## القرار
- SQLite المدمجة في Node (`node:sqlite`) — **من غير أي مكتبة جديدة**.
- ملف واحد: `database/data/suki.sqlite` (المجلد محمي أصلاً من الوصول من المتصفح).
- **مفتاح تشغيل**: `DB_DRIVER=sqlite` في `.env`. من غيره يفضل الموقع على JSON زي ما هو.

## التصميم
- جدول لكل مجموعة: `id TEXT PRIMARY KEY, pos INTEGER, data TEXT (JSON كامل)`.
  - السجل يتحفظ كامل كـ JSON → نفس الحقول والأسماء والـ IDs بالظبط، ومفيش route يتغير.
  - `pos` يحافظ على نفس الترتيب الحالي (الأحدث أولاً).
- `getById / update / delete` بالمفتاح مباشرة (أسرع).
- `update / insert / delete` بتحصل في خطوة واحدة متزامنة جوه transaction → **يختفي عيب lost update**.
- WAL + busy_timeout للأمان مع القراءة والكتابة في نفس الوقت.
- (المرحلة الجاية، لسه ما اتعملتش) دالة `db.transaction(fn)` للطلب + المخزون + المحاسبة مع بعض — **بموافقة منفصلة**.

## الاختبارات (على نسخة منفصلة فقط)
1. النقل: أعداد كل مجموعة قبل/بعد + مقارنة كل سجل.
2. كل الاختبارات الموجودة بـ `DB_DRIVER=sqlite`: fresh-store-e2e، step4، delete-probe، وغيرهم.
3. نفس الاختبارات بـ JSON للتأكد إن مفيش حاجة باظت.
4. تجربة كتابة متزامنة (طلبات كتير في نفس اللحظة) للتأكد إن مفيش تعديل بيضيع.

## الرجوع (Rollback)
- قبل التحويل: نشيل `DB_DRIVER` → الموقع يرجع JSON فوراً (الملفات ما اتلمستش).
- بعد التشغيل على SQLite فترة: `export-sqlite-to-json.js` يرجّع آخر بيانات لملفات JSON.

## المرحلة 2 (اتنفذت 2026-11-12 بموافقة المالك)

### 1. الطلب + المخزون + المحاسبة "كله أو ولا حاجة" — `db.atomic(fn)`
- `database/db.js` + `database/sqliteStore.js`: `db.atomic(t => {...})` — كتل متزامنة (من غير await) فمفيش طلب تاني يدخل في النص؛ أي خطأ يلغي كل اللي اتكتب. شغالة على SQLite (transaction) وعلى JSON (بتكتب في الآخر بس).
- `routes/orders.js`:
  | العملية | اللي بقى يتسجل مع بعض |
  |---|---|
  | طلب العميل | الكوبون + النقاط + المخزون (بيتراجع تاني لحظة الخصم) + الطلب. ونفس الطلب لو اتبعت مرتين خلال 20 ثانية يرجّع الأول |
  | الطلب اليدوي | المخزون + الطلب |
  | تغيير الحالة (تسليم / إلغاء) | قيد المحاسبة + عهدة المندوب + نقاط الولاء + كوبونات المكافأة + المخزون + الحالة |
  | إلغاء العميل | إرجاع المخزون والكوبون والنقاط + الحالة (لو لسه "اتسجل" فعلاً) |
  | تصحيح الحالة (المدير العام) | عكس آثار الحالة القديمة + آثار الجديدة + الحالة |
- قبل كده: خطأ في قيد المحاسبة كان بيتسجل في اللوج بس والطلب يبقى "اتسلّم" من غير قيد → دلوقتي بيرفض ومفيش حاجة بتتغير.
- كل عملية بتتأكد إن حالة الطلب ما اتغيرتش من حد تاني في نفس اللحظة (رسالة 409 واضحة).

### 2. نسخ احتياطي تلقائي — `utils/sqliteBackup.js`
- كل 6 ساعات (أول نسخة بعد التشغيل بـ 30 ثانية)، بيحتفظ بآخر 28 نسخة (~أسبوع) في `backups/sqlite/`.
- كل نسخة بتتعمل بـ `VACUUM INTO` (آمنة والمتجر شغال) وبتتفحص (`integrity_check`)، والنسخة البايظة بتتمسح.
- `.env`: `SQLITE_BACKUP_HOURS` (0 = إيقاف)، `SQLITE_BACKUP_KEEP`. نسخة يدوية: `node utils/sqliteBackup.js` (مش بتتمسح تلقائي).
- **الاسترجاع**: وقّف المتجر → امسح `suki.sqlite-wal` و `suki.sqlite-shm` → انسخ النسخة مكان `database/data/suki.sqlite` → شغّل.

### 3. `scripts/reset-trial-data.js`
- بيشتغل على JSON و SQLite (حسب `DB_DRIVER`)، بياخد نسخة احتياطية الأول، والتصفير كله في عملية واحدة "كله أو ولا حاجة".

### 4. تحويل المتجر الحقيقي (2026-11-12 10:18)
